# RSA Cryptographic Key Setup & JWKS Guide

This document outlines how to generate RSA 2048-bit private and public key pairs for signing OAuth 2.0 JWT access tokens (`RS256`), how to export them into the environment before running **MiniAuth**, and how external microservices / Resource Servers verify tokens via the JWKS endpoint.

---

## 1. Directory Structure & Security

MiniAuth stores cryptographic key files inside the `keys/` directory in the repository root.

```
MiniAuth/
├── keys/
│   ├── private_key.pem    # ⚠️ PRIVATE KEY - NEVER SHARE OR COMMIT TO GIT
│   └── public_key.pem     # 🌐 PUBLIC KEY - Shared via JWKS
```

> **Security Note:** The `keys/` folder and `*.pem` / `*.key` files are added to `.gitignore` to prevent secret leakage.

---

## 2. Generating RSA Key Pairs (OpenSSL)

### On Linux / macOS / WSL:
```bash
# 1. Create keys directory if it doesn't exist
mkdir -p keys

# 2. Generate 2048-bit RSA Private Key (PEM format)
openssl genrsa -out keys/private_key.pem 2048

# 3. Extract the Public Key (PEM format)
openssl rsa -in keys/private_key.pem -pubout -out keys/public_key.pem

# 4. Restrict private key file permissions (read/write only by current user)
chmod 600 keys/private_key.pem
chmod 644 keys/public_key.pem
```

### On Windows (PowerShell):
```powershell
# 1. Create keys directory if it doesn't exist
New-Item -ItemType Directory -Force -Path "keys"

# 2. Generate 2048-bit RSA Private Key
openssl genrsa -out keys/private_key.pem 2048

# 3. Extract the Public Key
openssl rsa -in keys/private_key.pem -pubout -out keys/public_key.pem
```

## 3. Exporting Keys Before Running the Server

You can configure the keys either via **File Paths** (recommended for local/VMs) or **Inline Environment Variables** (recommended for Docker, Kubernetes, Serverless, and CI/CD).

### Option A: Using `.env` File (Default & Simplest)
Add the following to `AuthorizationServer/.env`:
```dotenv
# Path relative to repository root or working directory
JWT_PRIVATE_KEY_PATH=keys/private_key.pem
JWT_PUBLIC_KEY_PATH=keys/public_key.pem
JWT_KEY_ID=miniauth-key-1
JWT_TTL=1h
```

---

### Option B: Exporting in Terminal / Shell

#### Linux & macOS (Bash/Zsh):
```bash
# Using File Paths:
export JWT_PRIVATE_KEY_PATH="keys/private_key.pem"
export JWT_PUBLIC_KEY_PATH="keys/public_key.pem"
export JWT_KEY_ID="miniauth-key-1"

# OR Using Inline PEM Strings:
export JWT_PRIVATE_KEY="$(cat keys/private_key.pem)"
export JWT_PUBLIC_KEY="$(cat keys/public_key.pem)"
export JWT_KEY_ID="miniauth-key-1"

# Run Authorization Server:
go run ./AuthorizationServer/cmd/server
```

#### Windows (PowerShell):
```powershell
# Using File Paths:
$env:JWT_PRIVATE_KEY_PATH = "keys/private_key.pem"
$env:JWT_PUBLIC_KEY_PATH = "keys/public_key.pem"
$env:JWT_KEY_ID = "miniauth-key-1"

# OR Using Inline PEM Strings:
$env:JWT_PRIVATE_KEY = Get-Content keys/private_key.pem -Raw
$env:JWT_PUBLIC_KEY = Get-Content keys/public_key.pem -Raw
$env:JWT_KEY_ID = "miniauth-key-1"

# Run Authorization Server:
go run ./AuthorizationServer/cmd/server
```

#### Windows (Command Prompt - CMD):
```cmd
set JWT_PRIVATE_KEY_PATH=keys/private_key.pem
set JWT_PUBLIC_KEY_PATH=keys/public_key.pem
set JWT_KEY_ID=miniauth-key-1

go run ./AuthorizationServer/cmd/server
```

## 4. Public Key Sharing: JWKS Endpoint

Once the Authorization Server is running, external Resource Servers (APIs, Client Applications) can fetch the public key dynamically:

### Endpoint:
```http
GET /.well-known/jwks.json HTTP/1.1
Host: localhost:8080
```
*(Also available under `GET /oauth/.well-known/jwks.json`)*

### Example JWKS Response (RFC 7517):
```json
{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "alg": "RS256",
      "kid": "miniauth-key-1",
      "n": "v1qQe...<base64url-encoded-modulus>...w",
      "e": "AQAB"
    }
  ]
}
```

---

## 5. Verifying Access Tokens with the Public Key

JWT access tokens generated by `/token` are signed with `RS256` and contain:
- Header: `{"alg": "RS256", "typ": "JWT", "kid": "miniauth-key-1"}`
- Payload Claims: `iss`, `sub`, `aud`, `client_id`, `scope`, `exp`, `iat`, `jti`.

Resource servers match the `kid` against `/.well-known/jwks.json` to verify token authenticity and integrity without needing any shared secrets!
